# FitLens 产品方案

## 一、用户问题

普通健身人群（想减脂、增肌或保持健康）在使用记录类产品时普遍遇到三类问题：

1. **饮食记录成本高**：手动搜索食物、估份量、算热量太麻烦，坚持不下来。
2. **信息分散**：训练、饮食、体重分别记在不同 App，看不到「摄入 vs 消耗 vs 体重」的因果关系。
3. **看不到反馈**：体重波动、训练是否有效，缺乏可视化趋势，容易放弃。

## 二、产品定位

「一句话」：**用 AI 把饮食记录成本从分钟级降到秒级，并把训练、饮食、身体数据汇总成一个每日可看、趋势可追的健身记录工具。**

- 中文优先，贴合本土饮食（米饭、面条、家常菜等）。
- 面向普通人，不做专业运动员级的功能复杂度。

## 三、核心功能（MVP）

1. **每日总览**：摄入 / 运动消耗 / 目标 / 剩余热量 + 今日训练状态 + 体重趋势。
2. **训练打卡**：记录类型、时长、消耗、感受。
3. **AI 食物识别**：拍照 → 估算（名称/份量/热量/营养素）→ **用户确认与修正** → 保存。
4. **身体数据**：体重 / 腰围 / 臀围 + 趋势图。
5. **个人资料**：昵称 / 头像 / 健身目标 / 身高年龄。

## 四、关键取舍

| 取舍点 | 决定 | 理由 |
|---|---|---|
| AI 结果是否直接采信 | **否，必须确认/修正后保存** | 热量估算天然有误差，直接采信会造成错误记录，损害信任 |
| 识别准确率 vs 协作成本 | 优先「可修正的协作流程」而非追求一步到位 | 让用户低成本纠正，比假装准确更诚实、更可持续 |
| 多端复用 vs 原生体验 | Expo 单代码库覆盖 Web + 移动 | 快速交付两形态，核心流程体验不受损 |
| 认证/AI 是否必需后端 | 是：账号密码、CAPTCHA、视觉识别均由后端完成 | 密码哈希、密钥、图片转发必须在服务端，不能放前端 |
| 单位 | 内部 kcal，界面「卡」 | 对齐用户口语，避免混淆 |

## 五、AI 协作流程设计（核心）

```
拍照/上传 → 模型估算 → [名称 + 份量 + 热量 + 营养素 + 置信度 + 不确定性说明]
    → 用户确认/修改（名称、份量、餐次；份量调整按每100g等比换算）
    → 保存为饮食记录（标注来源 ai / manual、是否模拟）
```

设计要点：
- **必须展示估算依据/不确定性**，不得把估算说成精确测量。
- **低置信度**时降低默认值、给出候选、要求确认（见 AI_EVALUATION.md）。
- **修正行为本身是产品信号**：修改率反映模型与用户期望的差距，也反馈到模型迭代。
